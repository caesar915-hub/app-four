FIG 01

Layer overview

The MVVM spine. SwiftUI Views observe @Observable ViewModels, which read and write the centralized RecordingStore and call domain services. AppServices bundles exactly 8 services; CloudSyncService and DoseLogService live outside the bundle — sync is read directly by SyncSettingsViewModel, dose logging is resolved only by App Intents. CloudKit mirroring is opt-in and off by default.

Model components — SwiftData schema

Six @Model types under SquirlSchemaV1. Recording is the aggregate root with three optional to-many relationships (arrays are optional per CloudKit's requirements). The container partitions models into a Synced store and a Local store; only Local models keep @Attribute(.unique).

FIG 05

Data flow — write path

The live pipeline runs inside CheckInViewModel: it saves the note, streams transcription itself, then hands the raw text to its composed ProcessingViewModel, which extracts and applies results to the Recording model. PendingTranscriptionService is the recovery lane — a serialized, oldest-first backlog drain triggered at launch, on foregrounding, and when the Whisper model finishes downloading.

FIG 06

Data flow — read & observation path

The reactive loop. SwiftData is the source of truth; RecordingStore.recordings is the observed collection; ViewModels derive view state from it; Views observe and re-render. User actions call back into the store, which mutates the context and saves — closing the loop. Opt-in CloudKit sync mirrors the Synced store across the user's devices.

    SD[("SwiftData<br/>ModelContext")] -- "loadRecordings()" --> Store["RecordingStore.recordings<br/>@Observable"]
    Store -- "derive" --> VM["ViewModels<br/>view state"]
    VM -- "observe" --> View["SwiftUI Views"]

Notes & caveats

  • iCloud sync (spec 038) is scaffolded and now has a working-tree UI consumer (SyncSettingsViewModel + ICloudSyncSection), but everything is uncommitted and the iCloud entitlement is not in the build target. CloudKit edges are drawn dashed and labelled opt-in.
  • JournalExportSection.swift exists on disk but the symbol is mounted nowhere (grep-verified); export UI lives in YourDataSection. It is omitted from Figure 02.
  • Field lists in Figure 03 are representative (the most load-bearing columns), not exhaustive — see DATA_MODEL.md for the full schema.
