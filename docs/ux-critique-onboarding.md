# Onboarding — UX/UI Critique & Brainstorm Brief

> **Source:** opus max-effort code review (six lenses) **(code-only — no screenshot)**. Nielsen heuristics **22/40**.

> **Status:** uncommitted working doc — feeds superpowers `brainstorming` → (if a feature emerges) Spec Kit.


## 1. What it is

A 3-page first-run flow presented as a `.fullScreenCover` from `RootContainerView` ([SquirlApp.swift#L60](app-four/App/SquirlApp.swift#L60)). It's a `TabView(.page)` with dots ([OnboardingView.swift#L15-L37](app-four/Views/Onboarding/OnboardingView.swift#L15)): (1) Welcome — hero waveform glyph + value prop + "Get Started"; (2) Microphone permission — request or "Skip for now"; (3) Download — fetches the Whisper transcription model (~150 MB) with a progress row, gating exit until complete (or offering Skip only on failure). State lives in `@Observable @MainActor OnboardingViewModel` ([OnboardingViewModel.swift](app-four/Views/Onboarding/OnboardingViewModel.swift)); completion writes `AppSettings.hasCompletedOnboarding = true`.


## 2. Verdict

AI-SLOP VERDICT: FAILS the slop test — and it fails on the single most identity-defining screen in the app. This is a textbook generic SwiftUI onboarding (centered SF Symbol → bold `.largeTitle` → grey `.font(.body)` subtitle → full-width `.borderedProminent` button), the exact "we gave up on typography/color" pattern DESIGN.md explicitly calls out as the category anti-pattern ([DESIGN.md#L17,L24](DESIGN.md#L17)). The damning part is that the Paper & Pollen system is fully built and shipping elsewhere — `Theme.background`, `Theme.accent`, `Theme.statusDone/danger`, `Typography.largeTitle/body` all exist ([Theme.swift](app-four/DesignSystem/Theme.swift), [Typography.swift](app-four/DesignSystem/Typography.swift)) — yet onboarding hardcodes `Color(.systemBackground)`, `Color.accentColor`, `.green`, `.red`, and `.font(.largeTitle/.body)` ([OnboardingView.swift#L38,L69,L74,L234,L244](app-four/Views/Onboarding/OnboardingView.swift#L38)). A user's first three seconds — which the design brief says must read as "relief, then permission" — instead render in iOS-default blue-tint-on-white with system fonts: it looks like a different, blander app than the one they're about to use. This is a P0 brand regression, not a nitpick. Beyond aesthetics: the permission step advances regardless of grant/deny and has no Settings escape hatch (a pattern the app already implements in CheckInView), and the copy leaks the internal model name "Whisper" and "~150 MB" to a non-technical, overwhelm-sensitive audience. The logic/state machine itself is sound and well-reasoned (gated exit, resumable retry, cancellation handling) — the failure is entirely in the presentation layer and a few UX edge cases. Heuristic score 22/40: functional and not broken, but off-brand and missing several first-run affordances.


## 3. Strengths (preserve)

- Download state machine is genuinely well-designed: exit is gated on `whisperComplete` so users can't enter a non-functional app, but a failure offers an explicit Skip so they're never trapped offline ([OnboardingView.swift#L275-L288](app-four/Views/Onboarding/OnboardingView.swift#L275), [OnboardingViewModel.swift#L26-L27](app-four/Views/Onboarding/OnboardingViewModel.swift#L26)). The inline comments justify the WHY, matching the project's comment policy.
- Retry is resumable, not restart-from-zero: `ensureDownloaded` short-circuits if the model is already on disk and verifies via filesystem + metadata, so a mid-download failure resumes ([OnboardingViewModel.swift#L43,L69-L91](app-four/Views/Onboarding/OnboardingViewModel.swift#L43)). The download `Task` is `[weak self]`, cancelled on completion/cancel, and `CancellationError` is handled distinctly from real errors ([OnboardingViewModel.swift#L48-L62](app-four/Views/Onboarding/OnboardingViewModel.swift#L48)).
- Concurrency is correct: the VM is `@MainActor`, `requestMicrophonePermission` awaits the async permission API cleanly, and the progress callback is typed `@MainActor (Double) -> Void` so UI mutations stay on the main actor ([OnboardingViewModel.swift#L5-L6,L38-L39,L71](app-four/Views/Onboarding/OnboardingViewModel.swift#L5)).
- Completion is idempotent and upsert-safe: it fetches an existing `AppSettings` and mutates it, only inserting if absent — won't create duplicate settings rows ([OnboardingViewModel.swift#L101-L112](app-four/Views/Onboarding/OnboardingViewModel.swift#L101)).
- Comprehensive `#Preview` coverage for every meaningful state (welcome, permission, in-progress, failed, completed) ([OnboardingView.swift#L303-L347](app-four/Views/Onboarding/OnboardingView.swift#L303)) — strong for design iteration.
- Decorative hero glyphs are correctly `.accessibilityHidden(true)` ([OnboardingView.swift#L70,L114,L167](app-four/Views/Onboarding/OnboardingView.swift#L70)), and the progress row uses `.accessibilityElement(children: .combine)` with a labeled checkmark ([OnboardingView.swift#L235,L249](app-four/Views/Onboarding/OnboardingView.swift#L235)).

## 6. Accessibility audit

- **P1** Hardcoded `.green`/`.red`/`.secondary` bypass Theme contrast-tuned tokens — Failure text uses `.foregroundStyle(.red)` on white ([#L186-187](app-four/Views/Onboarding/OnboardingView.swift#L186)) and completion uses `.green` ([#L234,L244](app-four/Views/Onboarding/OnboardingView.swift#L234)). The design system deliberately replaces raw system green/red with `Theme.statusDone`/`Theme.danger` ('warm clay, never raw red', [Theme.swift#L32-L36](app-four/DesignSystem/Theme.swift#L32)) which are tuned for the paper/loam backgrounds. On the warm-paper background these tokens are meant to maintain contrast; system `.red`/`.green` are not validated against it. Contrast of the actual rendered pairing needs pixel verification (needsScreenshot). `(OnboardingView.swift#L186-L187,L234,L244)`
- **P2** `Text(progress, format: .percent)` has no VoiceOver context label — During download the active row shows a bare percentage ([#L237](app-four/Views/Onboarding/OnboardingView.swift#L237)). The row combines children ([#L249](app-four/Views/Onboarding/OnboardingView.swift#L249)) so VoiceOver reads 'Whisper, 42%, Speech-to-text transcription' — acceptable, but there's no explicit progress semantics (e.g. `.accessibilityValue`) and the `ProgressView` value isn't separately announced. A 'downloading, 42 percent' phrasing would be clearer. Also the indeterminate `ProgressView()` + 'Downloading…' button-area state ([#L267-L271](app-four/Views/Onboarding/OnboardingView.swift#L267)) is not an actionable element and isn't labeled as a status. `(OnboardingView.swift#L237-L240)`
- **P2** Dynamic Type: hero icons are fixed-size and may collide with scaled text at AX sizes — Hero glyphs use `.font(.system(size: Metrics.IconSize.hero))` = fixed 72pt ([Metrics.swift#L32](app-four/DesignSystem/Metrics.swift#L32)), correctly flagged in Metrics as 'not Dynamic Type text'. That's fine for the glyph itself, but the surrounding `Spacer()`-driven `VStack` with large accessibility text sizes (titles + multi-line body) can overflow vertically with the fixed icon and bottom-padded buttons, with no `ScrollView` fallback. Layout at AX5 needs verification (needsScreenshot). `(OnboardingView.swift#L68,L112,L165)`
- **P3** Page-dot index control is not labeled for VoiceOver as step progress — `.page(indexDisplayMode: .always)` exposes dots but there's no 'Step 1 of 3' accessibility framing. VoiceOver users get generic page-control semantics with no sense of how many onboarding steps remain. `(OnboardingView.swift#L36)`

## 7. Logic / correctness

- **P2** Persisted permission state read from AVFoundation is never reconciled on appear — `permissionGranted` defaults to `false` and only updates after the user taps Grant ([#L18,L39](app-four/Views/Onboarding/OnboardingViewModel.swift#L18)). If the mic was already authorized (e.g. reinstall with retained TCC grant, or returning to onboarding), the button still shows 'Grant Microphone Access' and re-requests. There's no `.task`/onAppear reading `AVAudioApplication.shared.recordPermission` to seed the initial state. Minor, but it produces a redundant prompt path. `(OnboardingViewModel.swift#L18,L38-L39)`
- **P2** Completion writes settings but never verifies the save; a write failure silently strands the user — `completeOnboarding` uses `try? modelContext.save()` ([#L111](app-four/Views/Onboarding/OnboardingViewModel.swift#L111)) and fetch with `try?` ([#L105](app-four/Views/Onboarding/OnboardingViewModel.swift#L105)). If the save throws, the error is swallowed, `hasCompletedOnboarding` doesn't persist, and `RootContainerView.onChange(of: hasCompletedOnboarding)` ([SquirlApp.swift#L69](app-four/App/SquirlApp.swift#L69)) never fires — the cover would not dismiss and the user is stuck on the final screen with a button that appears to do nothing. No user feedback on failure. `(OnboardingViewModel.swift#L101-L112)`
- **P3** `modelsReady` computed property is defined but unused; gating logic lives in the View instead — `var modelsReady: Bool { whisperComplete }` ([#L27](app-four/Views/Onboarding/OnboardingViewModel.swift#L27)) is documented as the exit gate, but the actual gating is implemented via `DownloadPhase` in the View's `actionButtons` switch ([OnboardingView.swift#L255-L297](app-four/Views/Onboarding/OnboardingView.swift#L255)). The property is dead code (grep shows no other reference). Either wire it or remove it per the no-dead-code standard. `(OnboardingViewModel.swift#L26-L27)`
- **P3** Progress closure mutates VM state every tick across a possible actor hop — The `onProgress` closure captures `self` and sets `self.whisperProgress` ([#L52](app-four/Views/Onboarding/OnboardingViewModel.swift#L52)); it's typed `@MainActor` ([#L71](app-four/Views/Onboarding/OnboardingViewModel.swift#L71)) and the VM is `@MainActor`, so it's correct — but it depends on `AIModelService.download`'s `AsyncStream` and the `for await` loop ([#L81](app-four/Views/Onboarding/OnboardingViewModel.swift#L81)) not delivering at a rate that makes the per-tick cross-actor await a hotspot. Not a bug, a perf/isolation note. `(OnboardingViewModel.swift#L52,L71,L81)`

## 8. Motion / transitions

- **Page transition uses an untyped default animation** — `withAnimation { viewModel.currentPage = page }` — no `Motion` token. It's value-driven so Reduce Motion is auto-honored by SwiftUI, but the curve/duration is uncontrolled vs the app's `Motion.smooth` (0.4s). See P3 finding. `(OnboardingView.swift#L42)`
- **No bespoke transitions, matchedGeometry, or content-gated reveals — low motion risk** — Grep confirms the only animation is the single `withAnimation` at L42; there are no `.transition`, `.animation(_:value:)`, or `matchedGeometryEffect` usages. The `modelRows`/`actionButtons` swap on `phase` changes without explicit transition animation, so there's no hidden-render gated-reveal bug (the sections render purely from state, not from an onAppear-triggered reveal). The indeterminate `ProgressView()` spinners animate via the system and are correctly inert under Reduce Motion. `(OnboardingView.swift (whole file))`

## 9. What might be missing

- No persistence/observation of permission status on entry — can't reflect an already-granted mic (see logic finding). No 'Open Settings' affordance for the denied path, despite the app having that exact code in CheckInView.
- No error UI if `completeOnboarding`'s SwiftData save fails — the only failure surface is the download step; a settings-write failure leaves the user silently stuck.
- No way to revisit/replay onboarding from Settings (and no obvious 'you can change this later' messaging). Once `hasCompletedOnboarding` flips, the model download can only be triggered elsewhere — onboarding is single-shot.
- Welcome step has no Skip/secondary and the flow has no overall 'Skip setup' for users who want to explore first; download is the only place with deferral, and only on failure.
- No offline pre-check before the download step — if there's no connectivity the user must tap Download, wait, and fail before getting the Skip escape. A reachability hint up front would reduce a frustrating dead-end.
- No estimated time / data-cost reassurance beyond '~150 MB' — for a time-blind, friction-sensitive audience an indicator of 'about a minute on Wi-Fi' would lower abandonment anxiety.
- No mention of what happens to the app if they Skip the model (recording won't transcribe) — the consequence of skipping is invisible, so users can't make an informed choice.
- No haptic feedback on step completion / download success, despite a `Haptics` token file existing in the design system ([app-four/DesignSystem/Haptics.swift]) — a calm success haptic on 'completed' would fit the 'reward = captured' posture.
- Brand/scheme drift: deep-link scheme is still `whispernotes` ([SquirlApp.swift#L36](app-four/App/SquirlApp.swift#L36)) while onboarding copy says 'Squirl' — first-run is where naming consistency matters most.

## 10. Brainstorm seeds (→ /brainstorm)

1. What is the single job of first-run for an ADHD user — is it 'grant + download' (setup ceremony) or 'capture one thought in under 60s' (immediate reward)? Could the very first run BE a check-in, with permission/model handled lazily on first record?
2. How much of this should exist at all? Could permission and model download be deferred to the moment of first use (just-in-time), letting onboarding be a single warm welcome screen that honors the 'relief, then permission' brief?
3. What's the right posture when the mic is denied — gently insist (Settings deep-link), quietly proceed (typed notes still work), or explain the on-device privacy story harder to win the grant? Where's the line between reassurance and nagging for this audience?
4. Should the ~150 MB transcription model download be foregrounded as a gate at all, or backgrounded with a 'transcription will be ready shortly' affordance so the user can start capturing immediately on cellular/poor Wi-Fi?
5. What does a Paper & Pollen first-run actually look and feel like — warm paper, Fraunces headline, a breathing crescent instead of an SF symbol? What's the one signature visual that says 'this app is calmer than you' in the first 3 seconds?
6. How do we teach the abstract glyph language (sprout/lightning/aperture) — does onboarding preview it, or does the app trust users to learn it in context to keep first-run friction near zero?
7. Should onboarding be replayable/discoverable from Settings, and what's the model-management story long-term (re-download, delete to reclaim space, switch model size) — does any of that belong in the first-run mental model?
8. What's the failure philosophy across the flow — when the network dies, the save fails, or the mic is off, what's the calmest possible recovery that never makes a distractible user feel they 'broke' setup?
